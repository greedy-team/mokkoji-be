# 실행 절차

- 커맨드 인자(`$ARGUMENTS`)로 이슈 번호 또는 작업 요청 문장을 받는다. 인자가 없으면 사용자에게 요청하고 대기.
- 입력 모드 판별
    * `$ARGUMENTS`가 숫자(또는 `#숫자`)만으로 이루어지면 → 이슈 모드
    * 그 외 문장이면 → 작업 요청 모드

## 1. 사전 확인

* 아래 명령어를 병렬로 동시에 실행
    * `git status` (미커밋 변경사항 확인)
    * `git branch --show-current` (현재 브랜치 확인)
    * 이슈 모드만: `gh issue view <이슈번호> --json number,title,state` (이슈 형식·존재 여부 확인)
* 판단 및 분기
    * 미커밋 변경사항(스테이징/미스테이징/추적되지 않은 파일)이 있으면 자동으로 진행하지 않는다. 변경 파일 목록을 안내하고, 커밋 후 진행할지 사용자에게 확인 요청 후 대기.
    * 이슈 모드: 이슈가 존재하지 않으면 안내하고 종료. 이슈 제목(`작업코드: 작업내용`)에서 작업코드를 추출해 브랜치 접두어를 결정.
        * 작업코드 → 접두어 매핑 (`docs/work-convention.md` 참고)
    * 작업 요청 모드: 브랜치를 새로 만들지 않으므로 접두어 결정은 불필요. 현재 브랜치에서 작업한다.

## 2. dev 기준 최신화 (이슈 모드 전용)

* 작업 요청 모드는 이 단계를 건너뛴다. (현재 브랜치에서 그대로 작업)
* 이슈 모드: 항상 최신 dev에서 분기하기 위해 로컬 dev를 원격 기준으로 최신화한다. (오래된 브랜치/다른 기능 브랜치에서 분기하는 실수 방지)
* 절차
    1. `git fetch origin dev`
    2. 로컬 dev를 원격 dev로 fast-forward만 수행 (아래 중 상황에 맞는 방법)
        * 현재 dev 위에 있고 로컬 커밋이 없으면 `git switch dev && git merge --ff-only origin/dev`
        * fast-forward가 불가능하면(로컬 dev에 별도 커밋 존재 등) reset하지 않고 상황을 안내한 뒤 사용자 확인 요청

## 3. 작업 브랜치 준비

* 작업 요청 모드: 브랜치를 전환/생성하지 않고 현재 위치한 브랜치에서 그대로 작업한다. (dev 전환·새 브랜치 생성 안 함)
* 이슈 모드: 새 작업 브랜치를 준비한다.
    * 대상 브랜치명: `<접두어>/#<이슈번호>` (ex) `feat/#123`
    * `git branch --list "<브랜치명>"`로 존재 여부 확인 후 분기
        * 없으면: 최신 dev에서 생성 후 전환 `git switch -c <브랜치명> dev`
        * 이미 존재하면: 해당 브랜치로 전환 `git switch <브랜치명>` 후, 현재 dev와의 차이를 안내 `git log --oneline dev..<브랜치명>`
            * 기존 브랜치를 임의로 `reset`/`rebase`하지 않는다.

## 4. 작업 착수 (계획 확인)

* 구현 계획의 근거
    * 이슈 모드: `gh issue view <이슈번호>`로 제목·Summary·Todo 확인 → Todo 기반 구현 계획 정리
    * 작업 요청 모드: 요청 문장을 해석해 구현 계획 정리 (필요 시 관련 코드를 탐색해 범위 파악)
* 아래 형식으로 계획 제시

* [사용자 화면]
  ```
  (이슈 제목 또는 요청 요약)

  (구현 계획 — 항목별 접근 방법)

  원하시는 작업을 선택해주세요. ex)1

  [1] 이 계획으로 작업 시작

  [2] 취소

  (수정은 채팅으로 요청)
  ```
* 선택지 각 줄 사이의 빈 줄을 유지한 채 그대로 출력 (마크다운에서 단일 줄바꿈이 합쳐지는 것 방지)
* 사용자 확인([1]) 전에는 구현을 시작하지 않는다.

## 5. 구현

* 사용자가 계획을 승인하면 구현을 진행한다.
